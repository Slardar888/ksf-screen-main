# 页面布局合理性分析

> 分析对象：`ksf` 康师傅 MES 触摸屏系统（14 个页面，React + Tailwind，无手写 CSS）
> 分析口径：**全部为实测数据**，由 `.workbuddy/layout-analysis.mjs` 在 1920×1080 视口下逐页扫描 DOM 得出
> 判定基准（沿用项目已确立的原则）：
> 1. **不得有绝对定位** —— 内容区不允许出现 `position: absolute / fixed`
> 2. **盒内必须有内边距** —— 文字不得紧靠盒子边缘
> 3. **边必须对齐** —— 上下左右四条边不允许出现"差一点点"的错位
> 4. **间距必须成组一致** —— 同类元素之间的间距应当相等
> 5. **文字不得溢出** —— 内容必须完整显示

## 一点四、P1/P2/P3 的独立复核（不是靠判据改口径蒙过去的）

判据改动有"把真问题也过滤掉"的风险，所以对三条**最像是真问题**的条目做了
脱离审计脚本的独立实测（`.workbuddy/layout-analysis.mjs` 之外的测量）：

### (1) "登录 / 注料设置 / 料泵清洗 上下边只有 5–7px" —— 判定：假问题 ✅ 已核实

独立测量脚本对 6 个页面（操作画面 / 注料设置 / 料泵清洗 / 温度设定 / 超级用户 /
系统管理员）里**每一个文字叶子**同时算了两个距离：到自身盒子的距离，和到
**最近的有背景/边框的祖先盒子**的距离。结果：

| 测量对象 | 最小垂直墨迹间距 | 结论 |
| --- | --- | --- |
| 页面标题（6 页） | **10.7 / 11.9px** | 全站最小值，不贴边 |
| 按钮文字（操作画面） | 12.1 / 12.7px | 不贴边 |
| 按钮文字（注料设置、料泵清洗） | 16.1 / 16.7px | 不贴边 |

5–7px 那组数字来自**透明包裹层**：按钮里是
`<span class="pointer-events-none leading-none">`，它的排版盒在 1920×1080 下
只有 28 设计稿 px，而 `leading-none`（`line-height:1`）让字体的
**ascent+descent 超出 1em**，于是"元素矩形"（字面墨迹框）比盒子上下各多出约 5.6px。
但该包裹层 `overflow: visible`、无背景无边框，**不裁切、不可见**；
真正可见的按钮盒子给出的间距是 12.1–16.7px。

> 判据修正：垂直墨迹间距只对**有背景/边框的可见盒**计算。
> 实测全站 14 页"墨迹内边距 <8px 的可见文字盒"为 **0 个**。

### (2) "系统管理员中间列 4px 窄缝" —— 判定：原稿继承，收窄会更糟 ✅ 已核实

实测中间列单位文字的真实宽度（设计稿 px，字号 30）：

| 单位 | 单位盒 | 墨迹宽 | 盒内可用宽 | 结论 |
| --- | --- | --- | --- | --- |
| `袋/min` | x=768 宽 104 | **87.5** | 89.6 | 只剩 1.4px 余量 |
| `mm/袋` | x=768 宽 104 | **88.2** | 89.6 | 只剩 1.4px 余量 |
| `分钟` | x=768 宽 104 | 54 | 89.6 | 富余 |
| `mm` / `度` | x=340 宽 104 | 47.7 / 27 | 89.6 | 富余 |

也就是说 `UNIT_W=104` 已经是**不触发降字号的下限**：改成 96 会让「袋/min」
「mm/袋」降档，反而破坏"字号统一"。而单元格内部
`标签 176 + 控件 144 + 单位 104 = 424` 比单元格 384 多 40，
**原稿是 `154+154+110=418`，同样超**，属原稿继承。
可见侧的实测间距是：单位墨迹右缘 862、下一列标签托板 876 → **14px**，
无重叠、无裁切。

### (3) "角度监控上边缘错位 4px" —— 判定：原稿继承，已列入豁免 ✅ 已核实

实测单位「°」墨迹 1023–1032、右上角「操作画面」按钮文字墨迹 1101–1207，
中间空 **69px**；相交的只是单位文字盒（透明、无背景边框）与按钮盒子。
原稿卡片 640–1150 与按钮 1052–1256 本来就相交。
按"原稿所有视觉元素的布局位置不能修改"的约定保留，并在检测脚本里
列为**带理由的豁免项**（见 §八）。

## 二、绝对定位：已彻底解决 ✅

### 实测结果

14 个页面逐页扫描 `position: absolute | fixed`，**元素 0 个、伪元素 0 个**。

### 实现方式（为什么能做到）

原实现靠绝对像素坐标排版（`left/top/width/height`），本项目已替换为
**「CSS Grid + 原坐标换算成网格线号」**：

```
元素原坐标 (x, y, w, h)
   ↓ place()
grid-column: <c1+1> / <c2+1>
grid-row:    <r1+1> / <r2+1>
   ↓
Stage 是一个 repeat(N, minmax(0,1fr)) 的网格，铺满 100dvh
```

因此版面位置仍然 100% 由原设计稿坐标决定（保真度实测最大偏差 ≤3px），
但**没有任何一个元素使用绝对定位**。

### 全项目仅剩的 2 处 `absolute / fixed`（均不在页面布局内）

| 位置 | 用法 | 是否可接受 |
| --- | --- | --- |
| `VerifyPasswordDialog.tsx:75` | 弹窗遮罩 `fixed inset-0` | ✅ 可接受 —— 全屏模态遮罩天然需要脱离文档流，不属于任何页面的版面 |
| `styles.ts` 的 `BRACKET` | 弹窗面板的科技角标 `after:absolute` | ✅ 可接受 —— 纯装饰伪元素、`pointer-events-none`、不参与布局 |

**改进方法**：无需改动。若要求"连装饰都不要绝对定位"，可把 `BRACKET` 的角标
改为 4 个 `border-*` 组合的网格子元素 —— 但收益极低、代价是新增 4 个 DOM 节点，
**建议保持现状**。

> 需要提醒的是：本分析针对**页面布局**。如果在其它项目中复用本套图元，
> 请保持"网格落位"这一约束 —— 一旦有人往页面里加 `absolute`，整套等比缩放会立刻失准。

## 三、盒内内边距（padding）问题 ✅ 已修（本节为初版实测快照）

> **状态更新**：本节记录的"48 个按钮 padding 全为 0、3 个可见文字盒 padding 为 0"
> 已在 §1.5 的 P0 中全部修掉。复核值：无 padding 的可见文字盒 **0 个**、
> 墨迹内边距 <8px 的 **0 个**。本节保留原始实测数据，作为问题成因与修法依据。

### 3.1 按钮普遍没有内边距（**全局性、48 个按钮受影响**）

**问题**：`styles.ts` 的 `BTN` 常量**没有任何 `padding` 声明**。
原 CSS 实现里 `.hmi-btn` 有 `padding: 0.45em clamp(14px,1.4vw,26px)`，
在改用 Tailwind 类重写时被漏掉了。

**实测证据**（48 个按钮全部 `padding-left = 0`）：

| 页面 | 按钮 | 按钮宽 | 文字宽 | 文字到边框间距 | padding-left |
| --- | --- | --- | --- | --- | --- |
| 超级用户 | 横封原点确认 | 288 | 238.1 | **24.9px** | **0** |
| 超级用户 | 冷封原点确认 | 288 | 238.1 | **24.9px** | **0** |
| 超级用户 | 一键原点确认 | 288 | 238.1 | **24.9px** | **0** |
| 系统管理员 | 保养确认 | 252 | 158.8 | 46.6px | **0** |
| 操作画面 | 已关闭 ×3 | 216 | 119.1 | 48.5px | **0** |
| 主菜单 | 系统管理员 | 384 | 262.5 | 60.8px | **0** |

**当前是否有可见缺陷**：**没有**。因为按钮文字是**居中**的，且按钮都足够宽，
实测文字到边框的最小间距是 **24.9px**（真实像素），视觉上不会贴边。

**但这是规范性缺陷，必须修** —— 原因：
1. 内边距是**约束**，居中只是**结果**。一旦某个按钮文案变长（例如改成"横封原点确认（长按）"），
   文字会**立刻贴到边框**，而现在没有任何机制阻止它。
2. 触摸屏上文字贴边会显著降低可读性与可点性判断。
3. 全站其它元素（标签 12px、普通文字 8px）都有内边距，唯独按钮没有 —— **不一致**。

**改进方法**：

在 `styles.ts` 的 `BTN` 里补上与 `--pad-ctl` 同源的左右内边距：

```ts
export const BTN = [
  …
  "px-[calc(var(--u)*12)]",   // ← 新增：与标签托板/输入框统一为 12 设计稿 px
  …
].join(" ");
```

**安全性已实测验证**：最紧的按钮「横封原点确认」宽 288px、文字 238.1px，
加入 12 设计稿 px（= 16.2 真实 px）× 2 后可用宽度 255.6px > 238.1px，
**不会触发字号降档**，因此不会破坏"按钮字号全站统一 28"这条规范。其余 45 个按钮余量更大。

### 3.2 三处可见文字盒没有内边距

| 页面 | 元素 | 尺寸 | padding-left | 墨迹左距 | 说明 |
| --- | --- | --- | --- | --- | --- |
| 登录 | `登 录` 提交按钮 | 513×56 | **0** | 221.5px | 原生 `<button>`，未套 `BTN` 的 padding |
| 登录 | `M` logo | 72×72 | **0** | 23.9px | 单个字母居中，视觉可接受，但缺 padding 声明 |
| MES排程 | `确认排程` | 272×64 | **0** | 104px | 原生 `<button>`，仅统一了尺寸与字号 |

## 五、行内间距不相等 ⚪ 已逐条判定（本节为初版实测快照）

> **状态更新**：本节按"同一行带内 >1 种间距"判定。修正判据（只比同层叶子块）
> 并逐条人工复核后，6 页里的真问题 3 处（操作画面右列、超级用户右列、
> MES 按钮间距）已修；其余属**不同结构层级的间距差异**，逐条判定见 §1.5 的 P2 表。

判定方法：把同一行（`y` 相差 <8 设计稿 px）内的块按 `x` 排序，
相邻块之间的水平间距归一化后比较。

| 页面 | 实测同一行内的间距序列 | 问题 |
| --- | --- | --- |
| **超级用户** | `[8, 52, 32, 40, 4]` 与 `[8, 52, 32, 40, 56]` | ❌ **同一结构两行，最后一档一个 4 一个 56** |
| **IO监控** | `[16, 16, 424]` | ❌ 出现 **424px** 巨缝 |
| **系统管理员** | `[44, 44]`、`[4, 4]`、`[44, 4]` | ❌ 出现 **4px** 过窄间隙 |
| **操作画面** | `[20, 16, 4]`、`[20, 16, 8]` | ❌ 间距 20/16/4 三档混用 |
| **注料设置** | `[100, 48]`、`[120×6, 8]` | ❌ 6 个 120 之后突然出现 8 |
| **MES排程** | `[48, 48, 32]` | ❌ 32 与 48 不等 |
| **角度监控** | `[8, 80, 8]` | ❌ 8 与 80 相差 10 倍 |
| 主菜单 | `[96, 96, 96]` ×3 | ✅ 完全相等 |
| 料泵清洗 | `[40, 40]` | ✅ |
| 管制卡 | `[16, 16]` | ✅ |
| 操作画面（底部动作条） | `[72, 72, 72, 72]` | ✅ |
| 温度设定 / 预置计数 / 接头检测 / 登录 | 无 ≥3 块的同行 | — |

**改进方法（通用）**：
1. 每一行只允许**一种**间距值，并把它抽成该页的常量（如 `const GAP = 16`）；
2. 间距值必须是 **4 的倍数** —— 否则会被 4px 对齐网格吸附成两个交替值
   （本项目已踩过：步长 82 会退化成 18/22 交替，宽度 197 会被吸成 196/200）；
3. 出现"巨缝"（IO监控 424px）说明该行元素被 `justify-between` 或类似方式拉开 ——
   应改为**固定间距 + 剩余空间留在行尾**，而不是均分到所有间隙；
4. 出现"过窄间隙"（系统管理员 4px）说明元素宽度吃满了整行 ——
   应缩小元素宽度或换行。

## 九、文字层级一致性：标签字号 / 按钮字号

> 起因：用户反馈「MES 页面确认排程按钮的文字大小不对」「管制卡页面 label 的文字大小和对齐不一致」。
> 这两条都是**按角色分组比字号**才能发现的问题，前述六项判据都不覆盖，所以先补判据、再修问题。

### 9.1 根因一：引用了从未定义过的 CSS 变量（MES 确认排程）

`MesSchedulePage` 的「确认排程」原先是手搓的原生 `<button>`：

```tsx
style={{ fontSize: u("var(--fs-btn)"), ... }}   // u(p) = calc(var(--u) * p)
```

而 `--fs-btn` 在全项目里**没有任何地方定义过**。自定义属性替换失败会让整条
`font-size` 声明失效（invalid at computed-value time），字号退回浏览器默认值：

| 按钮 | 修复前 | 修复后 |
| --- | --- | --- |
| 获取订单 | 28 设计稿 px | 28 |
| **确认排程** | **16**（浏览器默认） | **28** |
| 返回主页 / 下一页 | 28 | 28 |

因为它是原生按钮、没有 `data-btn`，`spec.mjs`（按 `data-btn` 取按钮）**扫不到它**，
所以在此之前"按钮字号全站一种"一直是假绿。

**顺带做了一次全量排查**：把 `src/` 里所有 `var(--x)` 引用与所有 `--x:` 定义做差集，
除 `<Stage>` 运行时注入的 `--u / --ut / --title-size / --titlebar-h` 外，
只剩两个悬空引用，现已全部消除：

| 悬空引用 | 位置 | 影响 | 处理 |
| --- | --- | --- | --- |
| `--fs-btn` | `MesSchedulePage.tsx` | 字号退回 16px（可见） | 改用图元 `HmiButton variant="purple"`，紫色渐变逐字保留 |
| `--ctl-h` | `primitives.tsx` NumberField | `height` 失效退回 auto（恰好被 `CTL` 类的 56 兜住，肉眼看不出来） | 改为 `px(SPEC.ctl)`，并新增 `SPEC.ctl / SPEC.fsInput` 作为唯一数字源 |

`BUILD`/注释里提到的 `--pad-ctl`、`--fs-input` 同样从未定义，注释已一并更正。

### 9.2 根因二：标签字号按"放不放得下"各自缩档（管制卡）

`useFitText` 会在放不下时自动降档 —— 这本身是对的，但**没有任何判据要求
"同一页同角色的文字必须同号"**，于是格子偏窄的那几个标签就会悄悄变小。

管制卡实测（修复前）：

| 标签 | 渲染字号 |
| --- | --- |
| 时间：/ 生产日期： | 25 |
| 机台号： | **20**（请求 30，格子 108 宽放不下 4 个字） |
| 品名：/ 品号：/ 班别：/ 操作者：/ 包材：/ 标准袋长：/ 装箱量： | 35 |
| 序号：/ 框码绑定码： | **40** |
| 对齐 | 机台号：/ 序号：是 `align="center"`，其余标签是左对齐 |

修复后：**13 个标签全部 35 号、全部左对齐**。
为了做到这一点，把放不下的格子按实测字宽加宽（35 号实测：「生产日期：」175、
「时间：」105、时间戳 352.6、「机台号：」140、「JB301」97.8 设计稿 px）：

| 位置 | 改前 | 改后 |
| --- | --- | --- |
| 生产日期标签 / 日期值 | 0..192 / 192..384 | 0..220 / 220..440 |
| 时间标签 / 时钟 | 768..960 / 960..1280 | 768..908 / 908..1280 |
| 机台号组 | 面板 64..280，标签 64..172，值 172..280 | 面板 64..376，标签 64..240，值 240..376 |

> 注意还要算上 `LABEL` 类的 `padding 12` 与 `tracking 0.03em`：
> 「生产日期：」在 35 号下的实际占位是 `175 + 0.03×35×5 = 180.3`，
> 所以 204 宽的格子仍然差 0.3px 而降到 30 号 —— 第一次改完复测才发现，
> 最终取 220 宽（可用 196）。**只按"字数×字号"估宽度是不够的。**

### 9.3 新增判据：同页标签必须同号（两页已补齐，例外表清空）

`standards.mjs` 增加 H 项：同一页所有 `[data-text="label"]`（即带托板的标签）
渲染字号必须只有一档，否则判为未达标并打印每一档的实际文字。

先按"格子物理上放不下"登记过两页为例外，后来两页都按
**「按实测字宽加宽标签格 + 整页标签统一到能放下的最大档位」** 补齐了，
因此**例外表现在是空的**（机制保留，将来真加宽不了再登记并写明理由）：

| 页面 | 原状 | 处理 | 结果 |
| --- | --- | --- | --- |
| **操作画面** | 10 个 35 + 2 个 20（色标位调整：/ 冷封位调整：） | 右列标题格 148 → **196**，数值框 148 → **100**；全页标签统一 **30** | 12 个标签全部 30、全部左对齐 |
| **系统管理员** | 30 / 25 / 20 / 35 四档混用（且多行标签是居中的） | 标签列 176 → **208**，控件列 144 → **112**（列内总宽仍是 424，未新增溢出）；去掉 `labelSize={28}/{32}` 临时覆盖通道；全页标签统一 **25**、全部左对齐 | 11 个标签全部 25、全部左对齐 |

两处加宽的推导（都不是"看着差不多"，而是按实测字宽算的）：

```
操作画面  右列总宽 304；标签格 = 304 − 8 − 数值框
          数值框下限：输入框字号是 INPUT 类里写死的 34 号，NumberField
          **没有**自适应降档（useFitText 只用在 Text / HmiButton 上），
          所以格子窄了不会变小、而是三位数被截断。三位数在 34 号下约 61px，
          加 CTL 的 12×2 与 INPUT 的 0.2em×2 ≈ 98.6 → 取 100。
          → 标签格 196（可用 174.4 ≥ 「色标位调整：」在 30 号下的 166.9 ✓）
系统管理员 「加热在不运行时」7 字在 25 号下 180.25 + 托板 21.6 = 202 → 标签格 208
          （30 号要 240，而这一列 标签+控件+单位 只有 384、控件至少要 100 → 放不下）
          加宽的 32px 全部从控件列让出：208 + 112 + 104 = 424（与原来一致）
```

复核（`verify` 实测，尺寸为设计稿 px）：

```
操作画面   12 个 label 全部 30，左内缩全部 11.5
系统管理员 11 个 label 全部 25，左内缩全部 11.5（含原来居中的多行标签）
数值框     操作画面右列 100 宽、输入框仍是 34 号；系统管理员控件 112 宽、仍是 34 号
```

> **一个仍然存在的次要不一致**：操作画面的 R5 功能开关行有三个**无托板的
> plain 文字标签**（计数功能：/ 回吸功能：/ 辊筒计数：），它们渲染 25 号而
> 托板标签是 30 号。原因是硬约束而非疏漏：本行三组必须挤在 x=10 与
> 「清零」右缘 944 之间，`3×(标签 + 按钮 144) = 882`，只剩 52px 分给
> "标签加宽 + 组间距"，而标签要到 30 号得从 150 加宽到 172（需要 66px）；
> 按钮也不能再窄（「已关闭」4 字在 28 号下要 136px）。它们是另一种视觉样式
> （无托板，直接落在行背景上），不参与 H 项判据。

### 9.4 仍未统一的一项：管制卡的"数值"字号

标签已统一为 35，但**数值**仍有三档（35 / 40 / 25），这是被最长的数值卡住的物理约束：

| 数值 | 35 号下宽度 | 所在格子（减内缩后可用） | 结果 |
| --- | --- | --- | --- |
| 2026-09-12 12:34:56 | 352.6 | 372 − 16 = 356 | 35 ✓ |
| 2026-09-11 | 196.4 | 220 − 16 = 204 | 35 ✓ |
| JB301 | 97.8 | 136 − 24 = 112 | 35 ✓ |
| 1502AT11B / 醇香肉酱包16Y / 早 / 周税 / 80 / 001 | ≤ 233 | 288 − 16 = 272 | 40 ✓ |
| **经典红烧牛肉桶面酱包** | **350** | **288 − 16 = 272** | 只能到 **25** |

要让它也是 35，需要把该数值格加宽到 ≥ 374px；而左列字段宽 576（标签 288 + 值 288）、
右列从 672 开始，最多只能给到 320。除非改两列表单网格的列宽与留白，
否则只能把全页数值统一降到 25（比标签还小，视觉更差）。
本轮**未改动**，留给用户决定。
